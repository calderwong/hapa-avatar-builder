## Repeatable owner operation

`scripts/append-living-light-album-pass.mjs --plan=/absolute/plan.json` prepares
a bounded manifest against canonical Song IDs, all existing cut bytes and
exact native module revisions. `--apply` consumes that manifest, verifies it
again, backs up source projects/selected parents and the Journey database, and
uses LivingLightStore, Card custody, variant projection and saved-cut readers.
Writes are exclusive and append-only. Stable request IDs reconcile an interrupted
Journey save; conflicting children refuse. It stops at the first failed song.
It does not call models, analysis, rendering, workers or publication services.
It runs in one foreground process; custody handles close through their owner.

## Preview delivery correction and learning

The full-app check exposed a real owner-delivery mismatch: the API removed a
saved execution graph but retained its previous content fingerprint. The editor
then refused the otherwise valid local projection and returned to Legacy.
Delivery now keeps the immutable `source_fingerprint` while recomputing the
fingerprint of the actual delivered editing payload. Tampered content still
refuses. Living Light album cuts reuse the existing local editor fallback and
do not automatically start final-render certification when opened.

Reuse lesson: distinguish saved authoring coverage, usable preview and final
render acceptance. A healthy direct store read alone did not establish UI
delivery. No existing integration-board criteria are lowered or closed by this
album authoring batch.
