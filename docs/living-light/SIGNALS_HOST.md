## User-visible behavior and existing owners

The existing Living Light Workspace now shows **Song and stem signals**. Loading reads prepared measurements; **Prepare song and stems** explicitly starts the existing Echo preparation queue for the exact selected Song. Progress, cancellation and outcome checking are visible. Separate same-role assets and missing inputs remain separate rows. Preparation does not edit source audio/Songs or approve alignment.

`server/living-light-performance-port.mjs` adapts the existing preparation queue and publication store. Protected GET `/api/echos/living-light/performance?songId=…` reads a currently validated exact-asset publication. POST/GET/DELETE on `/api/echos/living-light/performance/prepare` prepare, observe or cancel it using Song/request identity. POST accepts an empty object and no client paths. Same request IDs reuse one job, including two concurrent calls awaiting input resolution. Another Song's job or a playback-audio job cannot be selected or cancelled through this adapter. The existing first-party loopback session/CSRF boundary and authenticated agent access still govern these routes; no token enters the browser.

After an ambiguous mutation failure, the UI retains its owned request ID and offers outcome checking rather than starting another preparation. Source changes/unmount supersede observers and attempt cancellation only of that owned request. Polling is bounded to 30 minutes. Request identity is transient: recovery across a crash/full reload is not yet qualified. Initial prepared reads use cancellation and generation guards; stale results cannot adopt another Song's measurements.

The Workspace owns one bounded feature cache. An explicit **Basic master loudness** selection leases a source bank, samples measured master RMS and applies bounded offsets through the existing native Core evaluation before painting. No second audible element, audio context or animation owner is created. Tunnel changes recreate the native renderer while retaining a warm bank; context restoration retains its lease. Runtime cleanup releases the lease and Workspace cleanup disposes the cache. Array ownership remains capped at 128 MiB with at most four inactive banks; it is not a decoder/JSON/graphics RSS bound.

Transient prepared bindings retain every exact asset but mark stem timing `alignment-unverified`, with no map. The cache key hashes the feature version, exact Song/policy/performance commitment, complete audible playback receipt and complete source binding. This keeps a fixed 77-character key for a 32-stem binding while still changing when its coordinates or configuration change. Performance fingerprints come from the trusted publication owner; a client-supplied revision is not independent source verification.
